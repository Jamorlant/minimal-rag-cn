# 接口集成与自动化工程实践

## HTTP 基础

HTTP 请求由方法、路径、请求头与请求体组成，响应包含状态码、响应头与响应体。

常见方法语义：GET 获取资源且应无副作用，POST 创建资源，PUT 全量更新，PATCH 局部更新，DELETE 删除。

状态码二百段表示成功，三百段表示重定向，四百段表示客户端错误，五百段表示服务端错误。

四百零一表示未认证，四百零三表示已认证但无权限，四百二十九表示触发限流。

请求头 Content-Type 声明请求体格式，JSON 接口通常为 application/json。

超时设置应显式配置连接超时与读取超时，避免请求无限挂起导致任务卡死。

重试只对幂等请求或明确可重试的错误生效，对四百段错误重试通常没有意义。

## 鉴权方式

Basic 认证把用户名密码做 Base64 编码放入请求头，必须配合 HTTPS 使用。

Bearer Token 在请求头 Authorization 中携带令牌，适合无状态服务端校验。

API Key 通常作为请求头或查询参数传递，需注意不要写入日志与代码仓库。

OAuth2 的授权码模式通过短期授权码换取访问令牌，适合需要用户授权的第三方应用。

令牌过期应实现刷新逻辑，刷新失败则重新走完整授权流程。

签名鉴权把参数与密钥按约定顺序拼接后做哈希，服务端用相同方式复核，可防篡改与重放。

## 请求封装

统一的 HTTP 客户端封装应集中处理超时、重试、鉴权、日志与错误映射。

错误处理区分可重试错误与业务错误，业务错误应携带错误码与可读提示。

分页接口要处理总数未知的情况，按返回条数判断是否继续翻页。

限流接口应实现退避策略，如指数退避配合随机抖动，避免多客户端同步重试。

请求与响应日志需脱敏，隐藏令牌、密码与个人信息字段。

接口变更应通过版本号或兼容字段演进，避免破坏已有调用方。

## 数据校验

入参校验包括必填、类型、长度、范围与枚举取值，尽量在调用外部接口前完成。

返回数据也要校验，字段缺失或类型异常时应视为失败而不是静默使用默认值。

金额与数量使用定点数或字符串传输，浮点数存在精度误差。

时间统一使用 ISO 8601 格式并携带时区，避免本地时间歧义。

去重键用于保证重复调用不会产生重复数据，配合幂等号写入服务端。

## 桌面自动化

桌面自动化通过模拟人工操作完成重复流程，适合缺少开放接口的系统。

元素定位优先级为稳定的属性标识、可访问性名称、文本内容，最后才用坐标点击。

坐标点击对分辨率与窗口位置敏感，界面稍有变化就会失效。

流程应加入显式等待而非固定睡眠，等待目标元素出现后再继续执行。

异常分支要覆盖弹窗、登录失效、网络超时与数据为空等常见情况。

每一步操作记录截图与关键变量，便于失败后快速定位。

流程设计遵循单一职责，把登录、查询、导出、上传拆成独立子流程便于复用。

## 流程健壮性

重试机制应区分瞬时故障与确定性失败，后者重试只会浪费时间。

循环处理列表数据时为每条记录生成唯一标识，失败后可断点续跑。

任务开始前检查运行环境，包括目标程序是否启动、账号是否登录、目录是否可写。

结束时清理临时文件与进程，避免长期运行积累资源占用。

对耗时流程设置总超时，防止个别卡死导致整批任务无法结束。

## 日志与监控

日志分级使用 DEBUG、INFO、WARNING、ERROR，生产环境默认输出 INFO 及以上。

关键节点记录开始时间、结束时间与处理条数，便于统计吞吐与瓶颈。

错误日志应包含堆栈、上下文参数与可复现步骤，仅记录「失败」无法定位问题。

监控关注成功率、平均耗时与失败分布，单一指标不足以发现退化。

告警应设置抑制与聚合，避免同一故障产生大量重复通知。

## 配置管理

配置与代码分离，环境相关参数通过环境变量或配置文件注入。

敏感配置不进入版本库，使用示例文件说明必需字段。

配置项需要校验与默认值，缺失关键配置时应在启动阶段快速失败。

多环境配置按环境名分组，避免手工修改导致环境串用。

## 测试与验收

单元测试覆盖纯逻辑函数，接口测试覆盖请求构造与响应解析，端到端测试覆盖主流程。

测试数据使用合成数据，不引入真实业务数据与个人信息。

断言要具体，既校验状态也校验关键字段内容，避免只判断请求是否成功。

回归测试在每次改动后运行，保证修复一个问题不引入新问题。

验收标准在需求阶段确定，包含正常路径、异常路径与性能指标。

## 并发与异步

并发任务数不是越多越好，过高的并发会让下游接口超时并放大失败率。

线程池适合阻塞式调用，异步协程适合高并发 IO，CPU 密集任务应交给进程池。

任务队列配合消费者可以削峰，生产端只负责入队，消费端按能力消费。

幂等设计是并发安全的基础，重复消费不会产生重复副作用。

分布式锁用于跨进程互斥，必须设置过期时间并考虑锁续期，避免死锁。

超时与取消要贯通到子任务，父任务取消后子任务应尽快释放资源。

## 文件与目录批处理

批量处理文件前先按扩展名与修改时间筛选，避免误处理无关文件。

文件锁可防止同一文件被两个进程同时写入，Windows 与类 Unix 的实现差异需注意。

大目录遍历使用生成器逐个产出路径，避免一次性构建超长列表。

文件名包含中文与空格时，命令调用应传参数列表而不是拼接命令字符串。

覆盖写入前备份到带时间戳的目录，可在一键回滚时快速恢复。

处理完成后生成清单文件，记录源路径、目标路径与状态，便于核对。

## 报表自动化

报表生成分为取数、计算、渲染与分发四步，任一步失败都应留下可追踪记录。

模板与数据分离，数据填充到占位符，避免每次修改格式都要改代码。

数值格式化统一小数位与千分位，不同国家地区的日期格式差异需按需配置。

导出后应做一次自检，核对行数、合计与关键单元格是否与源数据一致。

分发渠道要区分内部与外部，对外发送前必须完成脱敏与合规检查。

定时任务失败应通知责任人，同时保留上次成功产物避免下游断供。

## 异常恢复与幂等

外部系统超时后状态可能已改变，重试前应先查询确认，避免重复提交。

幂等号可由业务主键加操作类型生成，服务端据此判断是否已处理。

补偿逻辑处理「扣减成功但下游失败」这类中间态，需记录中间状态并定时扫描。

断点续跑依赖持久化游标，游标更新要与业务写入在同一事务或同一批次。

失败队列单独存放，支持人工重放与批量跳过，避免阻塞主流程。

恢复流程应可演练，未验证过的补偿逻辑在真实故障时往往不可用。

## 数据脱敏与合规

脱敏手段包括掩码、哈希、截断与假名化，选择取决于是否需要保持可关联性。

哈希脱敏需加盐，否则常见值可被字典反推。

测试环境应使用合成数据，直接拷贝生产数据是最常见的高风险行为。

导出文件应带水印或追踪标识，便于追溯外发来源。

日志与截图同样属于数据载体，含敏感信息的截图不得上传到工单系统。

权限最小化原则要求仅授予完成任务所需的字段与操作范围。

## 交付与文档

交付物包括代码、配置说明、运行手册与验收记录，缺一不可。

运行手册写清启动方式、依赖版本、常见故障与处理步骤。

配置项列出名称、含义、默认值与是否必填，避免使用者靠猜。

变更记录按版本列出影响范围与回滚方式。

监控接入说明包含指标名称与告警阈值，便于运维接手。

交接前做一次完整演练，由非开发者按手册独立跑通流程。

## 接口联调排查

先确认请求是否真正发出，抓包或打印完整 URL、方法、请求头与请求体。

状态码正常但数据为空时，检查参数名是否与文档一致，大小写与下划线差异很常见。

分页接口返回重复数据，通常是排序字段不唯一导致翻页漂移，应加入稳定主键排序。

签名校验失败多由参数排序、编码方式或时间戳格式引起，需按文档逐项比对。

证书问题表现为握手失败，应检查证书链是否完整以及系统时间是否正确。

限流错误需要区分短时突发与配额耗尽，前者退避重试，后者应等待配额恢复。

## 自动化流程设计原则

流程要可观测，关键步骤输出结构化日志，失败时能快速定位到具体行与具体字段。

流程要可恢复，任何一步中断后都能从检查点继续，而不是从头重跑。

流程要可配置，目标地址、账号、文件路径等参数外置，避免改代码才能换环境。

流程要可验证，每一步之后做一次轻量校验，例如记录条数或关键字段非空。

流程要可回滚，写入前保留原始数据，失败时可撤销已写入部分。

流程要可复用，把通用步骤封装为子流程，业务差异通过参数区分。

## 稳定性设计

对不稳定的外部系统设置熔断，连续失败达到阈值后短时间内快速失败，避免雪崩。

关键路径要有降级方案，例如接口不可用时读取上次缓存结果并标注数据时间。

资源使用要有上限，临时文件、连接与内存都要有回收策略。

长流程要能中断，提供停止信号并保证在安全点退出。

异常信息要可读，避免只抛出一个无上下文的错误码。

定期做故障演练，验证告警、切换与恢复流程是否真实可用。

## 团队协作与交付节奏

需求澄清阶段明确输入、输出与验收口径，减少后期返工。

开发前先对齐数据样例与边界条件，避免双方对字段含义理解不同。

联调阶段集中处理接口差异，问题记录在统一清单中逐项关闭。

上线前做灰度验证，先小范围运行并对比结果，再全量放开。

上线后保留观察窗口，监控关键指标是否出现异常波动。

复盘记录问题根因与改进项，形成可复用的检查清单。

## 需求分析与验收

需求输入要明确数据来源、处理规则、输出格式与验收标准，含糊的需求会反复返工。

规则类需求应给出正例与反例，仅描述「按规则处理」无法判断边界情况。

异常数据的处理方式必须显式约定，例如缺失字段是跳过、补默认值还是终止任务。

性能要求需要量化，例如处理十万条数据在多长时间内完成，否则无法验收。

验收清单逐条列出可验证项，验收时按清单打勾而不是凭印象判断。

变更需求要评估对已完成部分的影响，避免局部修改引发连锁问题。

## 日志排查案例

任务突然变慢时先看日志时间戳分布，若集中在某一步说明该步骤存在阻塞。

偶发失败要关注是否与特定输入有关，抽取失败样本单独重放能快速定位。

内存溢出多由一次性载入大文件或缓存未清理引起，可通过分块与及时释放解决。

编码问题表现为乱码或解析失败，统一以 utf-8 读取并检查源文件实际编码。

权限错误需区分文件权限与账号权限，前者检查目录访问，后者检查接口授权。

并发冲突常表现为数据覆盖或重复写入，应加入幂等键与行级锁。

## 自动化与人工的边界

规则明确且高频的流程适合自动化，判断复杂且低频的环节应保留人工。

自动化应保留人工干预入口，异常时暂停并通知，而不是强行继续。

人工环节要给出足够的上下文，包括失败原因与建议操作，减少反复沟通。

自动化结果需要可追溯，每条产出都能对应到输入与处理时间。

流程上线后持续统计人工介入率，介入率过高说明规则覆盖不足。

定期回顾自动化收益，维护成本超过收益的流程应考虑简化或下线。
