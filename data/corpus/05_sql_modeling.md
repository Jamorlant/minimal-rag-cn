# SQL 与数据建模基础

## 关系模型

关系数据库以表为基本单位，行表示记录，列表示属性，每张表通过主键唯一标识一行。

主键要求非空且唯一，复合主键由多列组合而成，可表达多对多关系的连接表。

外键约束保证引用完整性，删除父表记录前需先处理子表引用，或设置级联删除。

范式用于减少数据冗余。第一范式要求字段原子，第二范式消除部分依赖，第三范式消除传递依赖。

实际业务中适度反范式可减少联表查询，提高读取性能，代价是需要维护数据一致性。

视图是查询的命名封装，可简化复杂查询并限制列级访问权限。

## 查询语句

SELECT 语句执行顺序为 FROM、WHERE、GROUP BY、HAVING、SELECT、ORDER BY、LIMIT。

WHERE 过滤原始行，HAVING 过滤聚合后的分组，二者的执行阶段不同不能混用。

内连接返回两表都匹配的行，左连接保留左表全部行并对右表缺失补空值。

NULL 表示未知，任何与 NULL 的比较结果仍为 NULL，因此判断是否为空要用 IS NULL。

COUNT(*) 统计行数，COUNT(列) 忽略该列的 NULL 值，两者结果可能不同。

GROUP BY 后每组返回一行，SELECT 中只能出现分组列与聚合函数。

DISTINCT 作用于整行去重，多列时表示组合去重，开销高于分组去重。

UNION 会去重并排序，UNION ALL 保留重复且更快，数据已知不重复时优先使用后者。

子查询可出现在 SELECT、FROM、WHERE 中，相关子查询会对外层每行执行一次，注意性能影响。

窗口函数 ROW_NUMBER 按分组内排序编号，RANK 遇并列跳号，DENSE_RANK 遇并列不跳号。

LAG 与 LEAD 取前后若干行的值，常用于计算环比与间隔，默认值参数可在边界处避免 NULL。

## 索引与优化

B 树索引适合等值查询与范围查询，叶子节点通过链表相连支持有序扫描。

联合索引遵循最左前缀原则，查询条件跳过最左列时索引通常失效。

覆盖索引包含查询所需的全部列，可以避免回表，显著减少随机 IO。

索引并非越多越好，每个索引都会增加写入成本与存储占用。

对索引列使用函数或隐式类型转换会导致索引失效，应把计算移到常量侧。

EXPLAIN 可查看执行计划，重点关注是否全表扫描、是否使用临时表与排序、扫描行数估算。

大偏移量分页性能差，可用「上一页最大主键」的游标分页替代 LIMIT offset。

批量写入优于逐条提交，事务批次过大又会锁表时间过长，需要折中设置批大小。

## 事务与隔离

事务具备原子性、一致性、隔离性与持久性四项特征，提交后修改持久化，回滚则撤销全部变更。

读未提交隔离级别可能读到未提交数据，产生脏读。

读已提交解决脏读，但同一事务内两次查询可能得到不同结果，即不可重复读。

可重复读保证事务内多次读取一致，但可能出现幻读，即在范围查询中新增了行。

串行化最严格，通过锁或快照冲突检测保证完全隔离，并发性能最低。

乐观锁通过版本号或时间戳检测冲突，适合读多写少；悲观锁直接加行锁，适合冲突频繁的写场景。

死锁通常由两个事务以相反顺序加锁造成，数据库会检测并回滚其中一个事务。

## 数据建模实践

维度建模把数据分为事实表与维度表，事实表存放度量与关联键，维度表存放描述属性。

缓慢变化维用版本号或有效期字段记录属性变化，便于回溯历史状态。

宽表把多张表的关键字段合并，减少查询时的联表，适合报表与导出场景。

数据分层一般分为原始层、明细层、汇总层与应用层，每层职责清晰便于排查与复用。

主数据管理确保同一实体在不同系统中标识一致，避免重复与口径冲突。

数据字典记录字段含义、类型、取值范围与责任人，是跨团队协作的基础。

## 数据质量

完整性检查关注必填字段是否为空，唯一性检查关注重复记录，一致性检查关注跨表引用是否成立。

及时性关注数据从产生到可用的延迟，时效性要求高的报表需要更短的调度间隔。

数值异常可用分位数或三倍标准差识别，业务上还要结合量纲与合理区间判断。

数据校验应前置到写入环节，事后清洗的成本通常更高。

对账是数据质量的重要手段，通过总量、金额与条数比对发现丢失或重复。

## 报表与导出

报表口径应在需求阶段书面确认，包括统计范围、时间粒度、去重规则与空值处理方式。

时间字段统一时区与格式，跨时区场景需明确以哪个时区为准。

导出大数据量时采用分页或流式写出，避免一次性驻留内存。

导出文件应包含生成时间与筛选条件，便于使用者判断数据时效与适用范围。

敏感字段在导出前应脱敏，例如手机号仅保留后四位。

## 常见指标口径

日活指某自然日内有有效行为去重用户数，需先定义有效行为的判定条件。

留存率指某日新增用户在后续第 n 日仍有行为的比例，分母是当日新增用户数。

转化率指完成目标行为的用户占进入流程用户的比例，分母的选取直接影响结果可比性。

平均客单价等于总金额除以订单数，注意剔除退款订单还是保留会对结果造成差异。

同比与环比分别对比去年同期与上一期，季节性明显的业务更适合看同比。

分位数比平均值更能反映分布，长尾场景下平均值容易被少数极值拉高。

## 窗口函数进阶

窗口函数在其上方的 OVER 子句中定义分区、排序与框架，不改变结果行数。

PARTITION BY 按分组独立计算，未指定时整个结果集视为一个分区。

ROWS 与 RANGE 框架的区别在于前者按物理行偏移，后者按排序值范围偏移。

累计求和用 SUM 配合 ORDER BY 与默认框架，可得逐行累加值。

滑动平均用 ROWS BETWEEN 2 PRECEDING AND CURRENT ROW 取最近三行。

FIRST_VALUE 与 LAST_VALUE 可获取分区首尾值，后者需注意默认框架只到当前行。

NTILE 把分区按顺序切成若干桶，可用于分位数近似与分层抽样。

窗口函数不能直接写在 WHERE 中，需要先用子查询或公用表表达式计算再过滤。

## 公用表表达式与递归

WITH 子句把复杂查询拆成命名步骤，可读性显著优于深层嵌套子查询。

递归 CTE 由锚点查询与递归部分通过 UNION ALL 连接，用于展开层级与生成序列。

递归必须有终止条件，否则会无限循环，可设置最大递归深度作为保护。

CTE 在部分数据库中会被内联展开，不必然带来性能提升，需结合实际执行计划判断。

多次引用同一 CTE 时数据库可能重复计算，可改用临时表固化中间结果。

物化视图适合周期性复用的大聚合结果，但刷新策略需要与时效要求匹配。

## 查询优化案例

隐式类型转换会导致索引失效，例如字符串列与数字比较时应统一类型。

OR 条件跨不同列往往使优化器放弃索引，可改写为 UNION ALL 分别走索引。

大表关联应先过滤再关联，把条件下推到子查询可显著减少参与关联的行数。

排序与去重是主要开销来源，能用索引顺序满足时尽量避免额外排序。

统计信息过期会导致优化器选错执行计划，需要定期更新统计信息。

分区表按时间裁剪可减少扫描量，查询时必须显式带上分区键条件。

## ETL 与调度

抽取阶段要处理源系统变更，增量抽取依赖更新时间戳或变更日志。

转换阶段尽量在数据库内完成，减少数据搬运能显著提升整体吞吐。

加载阶段小批量提交可降低锁冲突，大批量提交则减少事务开销，需要平衡。

调度依赖要显式声明，上游未完成时下游应等待而不是重复重试。

任务失败应支持重跑与补数，补数逻辑要与增量口径保持一致，避免重复统计。

数据质量校验应作为调度的一环，校验失败时阻断下游并告警。

## 数据治理与权限

字段级权限控制到列，敏感列默认不对外暴露，需要单独申请授权。

行级权限按组织或区域过滤，避免同一份数据被越权查看。

数据血缘记录表与字段的来源去向，排查口径问题时能快速定位上游。

生命周期管理按时间归档冷数据，既满足合规要求又控制存储成本。

命名规范统一前缀与后缀，便于按主题域检索与管理。

变更管理要求结构变更走评审与灰度，直接改生产表容易导致上下游断裂。

## 常见口径陷阱

去重口径不一致会导致同一指标在两个报表中差异明显，需统一主键定义。

多对多关联会产生笛卡尔放大，统计前应确认关联键唯一性。

左连接后对右表字段做过滤会退化为内连接，应把条件放在连接条件中。

时间范围按自然日还是按滚动窗口计算，会让结果相差一天。

样本筛选条件在分子分母中必须一致，否则比率失去意义。

空值参与分组会单独成组，报表展示前应决定是合并还是隐藏。

## 实战查询场景

求每个用户最近一笔订单，可用窗口函数按用户分区并按时间倒序编号，取编号为一的记录。

求连续登录天数，可用日期减去行号的方式构造分组键，连续日期会得到相同差值。

求同比与环比，可用窗口函数 LAG 取上一期数值，再用当前值做比值，注意分母为零的处理。

求分组内前若干名，先用 ROW_NUMBER 编号再在外层过滤，避免用 HAVING 统计出现并列问题。

求两表差异记录，可用 NOT EXISTS 或 LEFT JOIN 后判断空值，前者通常更容易走索引。

求累计去重用户数需要按首次出现日期归属，直接对每日去重再累加会重复计算跨日回访用户。

## 数据仓库分层实践

原始层保留最细粒度与原始格式，便于重算，不做业务清洗。

明细层完成标准化与关联，统一时间、币种与主体标识，是大多数分析的基础。

汇总层按主题与粒度预聚合，控制数据量并提升查询速度，粒度需要在需求阶段确定。

应用层面向具体报表与接口，字段命名与口径完全贴合展示需求。

层间依赖应单向，禁止应用层反向依赖原始层，否则口径无法收敛。

每层都要有数据质量检查与血缘记录，否则问题定位只能靠人工排查。

## 模型设计细节

代理键与业务键并存，代理键用于关联与稳定引用，业务键用于对外展示。

状态字段建议用码值加字典表，避免把中文描述直接写进事实表。

金额字段统一币种与精度，跨币种场景应保存原币金额与折算汇率。

缓慢变化维需明确哪类属性变化才触发新版本，否则维度表会迅速膨胀。

拉链表记录生效与失效时间，查询时用时间点条件过滤得到当时的快照。

分区字段应作为查询条件显式传入，避免优化器无法裁剪分区。

## 权限与审计

查询审计记录访问人、时间、语句与返回行数，异常大批量导出应触发告警。

脱敏视图对外提供掩码后的字段，原始表权限仅授予必要角色。

敏感操作如删除与批量更新应走审批流，保留操作前后快照。

账号权限定期复核，离岗人员权限应及时回收。

数据共享优先提供聚合结果而不是明细，降低泄露风险。

## SQL 语法细节

字符串拼接在不同数据库中语法不同，标准写法使用双竖线，MySQL 用 CONCAT 函数，跨库脚本需要适配。

日期加减用日期函数而不是直接对字符串做运算，否则跨月跨年会出现错误结果。

大小写敏感性取决于数据库与排序规则，依赖大小写区分的逻辑应显式使用函数处理。

隐式排序不可依赖，未指定 ORDER BY 时返回顺序没有保证，分页查询尤其要注意。

聚合函数遇到全 NULL 的行可能返回 NULL 而不是零，展示前需要兜底处理。

除法运算要注意整数除法与除零问题，分子分母都应显式转换为浮点并处理零值。

子查询返回多行时不能直接用等号比较，应改为 EXISTS 或 IN。

## 指标分析案例

销售额下降需要拆解为量价与结构，先看订单数再看客单价，最后按渠道与品类下钻。

用户增长停滞要区分新增与留存，新增下降说明获客问题，留存下降说明产品或体验问题。

转化率下滑要定位具体环节，按漏斗各步骤的转化率逐段比较，避免只看整体。

复购率口径需明确统计周期与判定条件，周期不同会得到差异很大的结果。

库存周转天数上升可能来自销量下降或备货过多，需要结合采购与销售两侧数据判断。

异常波动先排除数据问题，再分析业务原因，否则容易在错误前提上做归因。

## 数据备份与恢复

备份策略需覆盖全量与增量，全量周期过长会导致恢复时间不可接受。

备份文件要验证可恢复性，未验证的备份在故障时往往不可用。

恢复演练应定期执行，明确恢复顺序与依赖关系。

删除操作应有软删除或回收期，直接物理删除难以挽回误操作。

跨环境恢复需脱敏，生产数据恢复到测试环境前必须处理敏感字段。

备份保留周期要符合合规要求，过期备份及时清理以控制成本。
