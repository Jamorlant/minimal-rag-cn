# Git 与工程协作实践

## 版本库基础

Git 把每次提交保存为不可变快照，提交通过父指针形成有向无环图，分支本质上只是指向某个提交的可移动指针。

工作区存放当前编辑的文件，暂存区记录下一次提交将要包含的内容，本地仓库保存已提交的历史，三者需要分别理解。

git add 把改动放入暂存区，git commit 把暂存区内容生成一次提交，跳过 add 直接提交只会包含已被跟踪的文件。

git status 展示工作区与暂存区相对 HEAD 的差异，是每次操作前最应该先看的命令。

git diff 比较工作区与暂存区，git diff --staged 比较暂存区与最近一次提交，两者用途完全不同。

git log --oneline --graph 可以直观看到分支合并关系，排查历史问题时比默认输出更有效。

git show 查看某次提交的具体改动，配合文件路径参数可以只看某个文件的变更。

## 撤销与恢复

git restore 用于撤销工作区改动，git restore --staged 撤销暂存，两者都不会改写历史。

git reset --soft 只移动分支指针，保留暂存区改动，适合把上一次提交拆成多次。

git reset --mixed 是默认模式，移动指针并重置暂存区，工作区内容保留。

git reset --hard 会丢弃工作区改动，属于破坏性操作，执行前应确认没有未提交内容。

git revert 生成一次反向提交来抵消某次变更，适合已经推送的提交，因为不改写历史。

git reflog 记录 HEAD 的移动轨迹，误操作后通常可以通过它找回丢失的提交。

stash 把未提交改动暂存起来，切换分支处理紧急问题时常用，恢复后用 stash drop 清理。

## 分支与合并

主干分支保持随时可发布，功能开发在独立分支上进行，完成后通过合并请求回到主干。

功能分支命名包含改动主题，便于在分支列表中快速识别用途，长期分支应定期与主干同步。

快进合并只移动指针，不产生合并提交，历史呈线性；非快进合并会生成一个合并节点。

变基把当前分支的提交依次重放到目标分支之上，历史更线性，但会改写提交哈希，已共享的分支不宜变基。

合并冲突需要人工判断保留哪部分内容，解决后必须实际运行验证，不能只看冲突标记是否删除。

cherry-pick 把指定提交复制到当前分支，适合把修复同步到多个发布分支。

合并前先拉取远端最新内容，避免在本地完成大量工作后才发现存在冲突。

## 提交信息规范

提交信息应说明改动的目的而不是罗列文件，阅读者关心的是为什么改。

首行控制在较短长度内概括改动，正文补充背景、影响范围与验证方式。

类型前缀可区分新功能、修复、重构、文档与测试，便于生成变更记录。

一次提交只做一件事，把格式化与功能改动混在一起会让评审难以聚焦。

避免提交生成物、缓存与本地配置，通过忽略文件规则统一排除。

提交前运行本地检查，保证每次提交都处于可运行状态，便于二分定位问题。

## 远程协作

远端仓库是团队共享的权威副本，推送前先确认分支与目标远端是否正确。

首次推送需要设置上游分支，之后可以直接使用简写命令推送与拉取。

拉取默认可能产生合并提交，团队应统一使用合并还是变基策略，避免历史风格混杂。

强制推送会覆盖远端历史，只能用于个人分支，且应使用带保护的强制推送形式。

拉取请求应包含改动背景、验证方式与影响范围，评审者据此判断风险。

评审意见应具体到代码位置并给出修改建议，只说「有问题」无法推进。

## 忽略与环境隔离

忽略文件规则按路径模式匹配，已跟踪的文件不会因为加入规则而自动停止跟踪。

本地环境配置与密钥不得入库，应提供示例文件说明字段含义。

依赖目录与构建产物不入库，通过依赖清单和构建脚本还原环境。

大文件应使用专门的对象存储或大文件扩展，直接提交会永久增大仓库体积。

忽略规则变更后应检查是否误忽略了必要文件，尤其是配置模板与测试数据。

## 冲突排查与历史定位

二分查找用 git bisect 在提交区间内快速定位引入问题的提交，每次把区间减半。

git blame 显示每行最后修改的提交，适合追溯某段逻辑的变更原因，但不能替代理解代码。

git log -S 按内容搜索提交，可找到某个字符串是何时被加入或删除的。

对比两个分支的差异用三点语法，可排除目标分支已有的提交，得到当前分支真正新增的改动。

大型重构后再定位历史较困难，应在重构提交中只做结构调整，不混入行为变化。

标签用于标记发布点，附注标签可保存发布说明与签名信息。

## 文档写作与项目说明

项目说明开头用一句话讲清定位，让读者在十秒内判断是否相关。

安装与运行步骤要可直接复制执行，避免「先配置环境」这类含糊表述。

示例输出应来自真实运行结果，虚构的输出会让使用者误判功能。

局限说明要明确未实现的能力与降级方案，比夸大能力更能建立信任。

目录结构说明标注每个目录的职责，减少阅读源码时的搜索成本。

评测数字应注明样本规模与评分口径，缺失口径的数字不具备可比性。

变更记录按版本列出新增、修复与破坏性改动，方便使用者评估升级成本。

## 发布与回滚

发布前在预发环境验证主流程，数据与配置尽量贴近生产，避免只在本地可用。

发布清单包含变更内容、影响范围、验证结果与回滚步骤，缺一项都不算准备完成。

回滚方案必须实际演练过，未经验证的回滚在故障时往往无法执行。

灰度发布先放小流量，观察错误率与耗时，再逐步放大。

数据库变更需要向前兼容，先加字段再改代码，避免回滚后结构不匹配。

发布后保留观察窗口，确认指标平稳再关闭变更单。

## 代码评审要点

评审先看整体思路是否与需求一致，再看实现细节，避免陷入格式讨论。

重点关注边界条件、错误处理、资源释放与并发安全这四类高风险问题。

重复逻辑应抽取复用，但不要为两处相似代码强行抽象，耦合过紧会增加后续成本。

命名应表达意图，缩略词与单字母变量只在极小的作用域内使用。

测试是否覆盖关键分支是评审重点，缺少测试的功能改动风险更高。

评审意见区分「必须修改」与「建议」，避免把风格偏好写成阻塞项。

## 项目结构与可运行性

入口文件放在根目录，使用者无需猜测启动方式。

核心逻辑与命令行外壳分离，方便被其他程序调用与单独测试。

配置集中在明确的位置，默认值要能支撑开箱即用。

示例与测试数据放在独立目录，避免与真实配置混在一起。

依赖声明完整，缺失依赖时给出清晰的安装提示而不是直接抛出导入错误。

首次运行能自动生成必要的索引或缓存，减少手工步骤。
